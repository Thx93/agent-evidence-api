# x402 payment

Paid access to Agent Evidence API uses **x402 + USDC on Base**. There are no API
keys, no subscriptions, and no user accounts — the payment *is* the
authentication.

> **Status.** The x402 gate is implemented at the edge in
> `apps/worker/src/index.ts` using the official `@x402/hono`, `@x402/evm`, and
> `@x402/core` packages. What has **not** been demonstrated is a real on-chain
> settlement: no mainnet payment and no funded Base Sepolia payment has been
> executed against a deployed instance in this repository's history. Treat the
> integration as implemented-but-unverified on-chain. See
> [§9 Status](#9-status-and-remaining-configuration).

---

## 1. Why the protocol, not a bespoke scheme

SPEC §11 is explicit: *"Do not invent a custom payment protocol"* and *"Use the
current official x402 integration supported by the chosen Cloudflare/MCP
implementation rather than hand-implementing the protocol unless absolutely
necessary."*

The implementation therefore wires the official middleware rather than
hand-rolling verification. In `apps/worker/src/index.ts`:

```ts
const facilitator = new HTTPFacilitatorClient({ url: env.X402_FACILITATOR_URL });

const resourceServer = new x402ResourceServer(facilitator).register(
  env.X402_NETWORK as Network,
  new ExactEvmScheme(),
);

const gate = paymentMiddleware(
  {
    [routeKey]: {
      accepts: {
        scheme: "exact",
        price: priceString(env.X402_PRICE_USD),
        network: env.X402_NETWORK as Network,
        payTo: env.X402_RECIPIENT,
      },
      description: "Agent Evidence API — structured, cited web evidence",
    },
  },
  resourceServer,
);
```

The gate is applied to exactly two route keys:

- `POST /v1/evidence`
- `POST /mcp` — and only when the JSON-RPC body contains `tools/call` for
  `research_evidence` (see [`mcp.md` §3](./mcp.md#3-what-is-free-and-what-is-paid))

The middleware instance is **memoised**: it is rebuilt only when the tuple
`routeKey | recipient | network | price | facilitator` changes. Rebuilding it per
request would re-sync with the facilitator on every call.

## 2. The payment flow

```text
Agent
  │
  │  1. POST /v1/evidence              (or tools/call research_evidence)
  ▼
Worker  ──▶  no valid payment
  │
  │  2. 402 Payment Required  +  x402 payment requirements
  ▼
Agent
  │
  │  3. pays USDC on Base / Base Sepolia
  │     to X402_RECIPIENT
  ▼
Agent
  │
  │  4. retries the same request with `payment-signature: <proof>`
  ▼
Worker
  │
  │  5. x402 verification (via X402_FACILITATOR_URL)
  ├── invalid  ──▶ 402 PAYMENT_INVALID
  ├── expired  ──▶ 402 PAYMENT_EXPIRED
  ▼
  │  6. forwarded to the backend with x-backend-auth
  ▼
Backend
  │  7. EvidenceService executes: validate → fetch → extract
  │     → normalise → assess → structured response
  ▼
Worker  ──▶  8. 200 with the EvidenceResponse, plus `payment-response`
```

Step by step:

1. **Request without payment.** The client calls `POST /v1/evidence` (or the
   paid MCP tool) with no proof.
2. **`402 Payment Required`.** The x402 middleware answers with the payment
   requirements for the configured network, price, and `payTo` address. The
   Worker's canonical error envelope carries `PAYMENT_REQUIRED` with HTTP 402.
3. **Agent pays USDC.** The agent's wallet layer settles the exact amount in
   USDC on the configured network. The recipient needs only a **public
   address** to receive — no private key is involved on the server side.
4. **Retry with proof.** The agent repeats the identical request, attaching the
   payment proof in the `payment-signature` header.
5. **Verification.** The middleware verifies the proof through the configured
   facilitator. A proof that fails verification becomes `PAYMENT_INVALID`; an
   expired one becomes `PAYMENT_EXPIRED`. Both are HTTP 402.
6. **Forwarding.** Only after verification does the Worker call the backend,
   attaching `x-backend-auth: <BACKEND_AUTH_SECRET>` and forwarding the
   `payment-signature` header so the backend can record settlement if it needs
   to.
7. **Execution.** `EvidenceService` runs the evidence pipeline. The payment layer
   is never involved in this step — SPEC §39 keeps x402 out of the core engine.
8. **Response.** The evidence document is returned, and the `payment-response`
   header from the backend is passed back through to the client.

### Payment-related error codes

| Code | HTTP | Meaning |
|---|---|---|
| `PAYMENT_REQUIRED` | `402` | Payment is required to access this resource. |
| `PAYMENT_INVALID` | `402` | The supplied payment could not be verified. |
| `PAYMENT_EXPIRED` | `402` | The supplied payment has expired. |

These are three of the eighteen stable codes in `packages/schemas/src/errors.ts`.
The Worker maps each code to its status via `ERROR_HTTP_STATUS`.

## 3. Configuration variables

All four x402 variables are read from the Worker's `env` bindings.

| Variable | Purpose | Example / default |
|---|---|---|
| `X402_NETWORK` | CAIP-2 identifier of the settlement network. | `eip155:84532` (Base Sepolia, test) or `eip155:8453` (Base, production). |
| `X402_RECIPIENT` | **Public** receiving address. `payTo` in the payment requirements. | `0x…` — a public address you control. Never a key. |
| `X402_FACILITATOR_URL` | x402 facilitator used for verification and settlement. | `https://x402.org/facilitator` |
| `X402_PRICE_USD` | Price per evidence request, in US dollars. | `0.003` |

One further Worker variable controls the development bypass:

| Variable | Purpose |
|---|---|
| `DEV_BYPASS_PAYMENT` | Set to the literal string `true` to skip payment gating. Guarded — see §6. Never set in a deployed environment. |

And one variable belongs to the Worker→backend boundary rather than to
payments, but is configured alongside them:

| Variable | Purpose |
|---|---|
| `BACKEND_AUTH_SECRET` | Server-to-server shared secret. Set with `wrangler secret put`, never in `wrangler.jsonc`. |

### Price formatting

`X402_PRICE_USD` is normalised by `priceString()` before being handed to x402:

- a leading `$` is stripped if present, so both `0.03` and `$0.03` work;
- decimals are PRESERVED (USDC's 6 decimals, shortest exact form), so `0.003` stays `$0.003`;
  an earlier `toFixed(2)` rendered `0.003` as `$0.00` and asked buyers for nothing;
- if the value is missing, non-numeric, or not positive, the paid route **refuses
  to serve**. It does NOT substitute a price.

That last behaviour is deliberate and was changed. The old code fell back to a
hard-coded `$0.03`: a stale duplicate of a config value, and a silent substitution
inside a payment path, where a typo would have charged a price nobody chose. A paid
service that cannot determine its price must fail, not guess.

### Pricing principle

SPEC §12 asks for a very small MVP price with a configurable default of
approximately **$0.003 per evidence request**, and states plainly that the final
commercial price is not fixed. `0.003` is the default in
`packages/core/src/config.ts`, in `.env.example`, and in the Worker's
`wrangler.jsonc` vars.

The `packages/core` default network is `eip155:84532` (Base Sepolia). That is the
safe default: an unconfigured deployment is on testnet, never accidentally on
mainnet.

## 4. Networks and settlement token

| Environment | Network | CAIP-2 identifier |
|---|---|---|
| Test | **Base Sepolia** | `eip155:84532` |
| Production | **Base** | `eip155:8453` |

The settlement token is **USDC** in both cases. The `/` capabilities endpoint
reports this explicitly as `payment.asset: "USDC"`; it is not configurable,
because SPEC §11 fixes it.

`eip155` is the CAIP-2 namespace for EVM chains; `84532` and `8453` are the
Base Sepolia and Base chain IDs.

The Worker also hard-codes the production network identifier for one purpose
only — the bypass guard:

```ts
/** Base mainnet. Payment can never be bypassed on this network. */
const MAINNET = "eip155:8453";
```

## 5. Separate test and production configuration

SPEC §12: *"For testnet use a clearly separate environment/config. Do not mix
testnet and production wallet configuration."* SPEC §32 asks for Worker
configuration for both `base-sepolia` (development) and `base` (production).

`apps/worker/wrangler.jsonc` is structured to enforce that separation:

| Environment | Activation | Network | `DEV_BYPASS_PAYMENT` | Backend origin |
|---|---|---|---|---|
| **production** (top-level `vars`, shipped by a bare `wrangler deploy`) | `wrangler deploy` | `eip155:8453` (Base) | **absent** | your protected origin |
| **dev** (`env.dev`) | `wrangler dev --env dev` | `eip155:84532` (Base Sepolia) | `true` | `http://127.0.0.1:8080` |
| **test** (`env.test`) | `wrangler dev --env test` | `eip155:84532` (Base Sepolia) | absent — payment **is** required | `http://127.0.0.1:8080` |

Three details that matter:

- **Wrangler does not inherit top-level `vars` into a named environment.** Every
  variable the Worker reads is therefore repeated in each `env` block. Omitting
  one yields `undefined` with only a warning, not an error — so a missing
  variable shows up as a `NOT_CONFIGURED` response, not a startup failure.
- **`BACKEND_AUTH_SECRET` is deliberately absent from `wrangler.jsonc`.** It is a
  secret and must come from `wrangler secret put BACKEND_AUTH_SECRET`. Putting it
  in the config file would commit it to the repository.
- **Never use production wallet configuration in development.** The production
  block is mainnet; the dev and test blocks are Sepolia. Do not copy a mainnet
  recipient into a dev block, and do not put a testnet-funded key anywhere near
  mainnet.

> **Configuration defect to fix before deploying.** `apps/worker/wrangler.jsonc`
> currently contains **literal test-recipient addresses** in its `env.dev` and
> `env.test` blocks, and the same literal in both. SPEC §33 says *"Do not invent
> a wallet address"* and AGENTS.md §6 forbids committing wallet configuration.
> Those two values must be replaced with placeholders (`0x…` / a documented
> local-only value) before this file is published or deployed. The production
> block uses a zero address placeholder, which is also not a real recipient but
> fails loudly instead of pointing at a third party. No real address is
> reproduced in this document.

## 6. The development payment bypass

Running the full pipeline locally should not require testnet funds, so a bypass
exists — but it is **doubly guarded**:

```ts
function devBypassActive(env: Env): boolean {
  return env.DEV_BYPASS_PAYMENT === "true" && env.X402_NETWORK !== MAINNET;
}
```

Both conditions must hold:

1. `DEV_BYPASS_PAYMENT` is exactly the string `"true"`, **and**
2. `X402_NETWORK` is not `eip155:8453`.

Consequences, stated plainly:

- **The bypass is disabled on mainnet, unconditionally.** Even if
  `DEV_BYPASS_PAYMENT=true` leaks into a production environment, the second
  condition fails on Base mainnet and payment gating stays on.
- The bypass applies to `POST /v1/evidence` and to paid MCP calls.
- When active, the Worker adds a visible marker to the response so a bypassed
  response can never be mistaken for a paid one: the `x-dev-payment-bypass:
  active` header is set on proxied responses, and an `X-Dev-Payment-Bypass:
  active` header is set on bypassed MCP calls. The marker is suppressed for
  `/health`.
- The bypass is a **local development affordance**. Never enable it in a deployed
  environment. Correct configuration in the `dev` env block is: Sepolia network
  **and** the bypass flag together — which is exactly what `env.dev` does.

## 7. No API keys, no accounts — by design

This is a product decision, not an omission.

SPEC §11: *"Do not create API keys for paid access. Do not create user
accounts."*
SPEC §38 lists what an agent should never have to do: create an account, create a
password, request an API key, subscribe to a monthly plan, or contact sales. The
preferred experience is:

```text
discover tool → call tool → 402 → pay USDC → retry → receive evidence
```

So there is no signup form, no key issuance, no key rotation, no billing
dashboard, no subscription state, and no organization model. Payment is the only
credential, and it is verified per request.

### The one secret in the system is not a customer credential

`BACKEND_AUTH_SECRET` might look like an API key. It is not. It authenticates the
**Worker to the backend** — an internal hop that customers never see and never
hold. Its purpose is the opposite of a customer key: it exists so that a customer
*with* a wallet cannot bypass the payment gate by calling the backend origin
directly. See [`security.md`](./security.md) for the origin-protection model.

No secret is ever exposed to a customer, returned in a response, or written to a
log.

## 8. Private keys

The rules here are absolute.

- **Never commit a private key.** Not to `wrangler.jsonc`, not to `.env`, not to
  a test file, not to documentation. SPEC §11: *"Never commit a wallet private
  key."*
- **Receiving needs no key at all.** `X402_RECIPIENT` is a **public address**.
  The service verifies payment through the facilitator; it never signs anything,
  so it never needs signing material. Only the client paying needs a wallet.
- **The service never stores a customer's private key.** SPEC §11: *"Never store
  a customer wallet private key."*
- **`X402_TEST_PRIVATE_KEY` is testnet-only.** It is declared in `.env.example`,
  blank by default, and documented as a disposable Base Sepolia wallet used by
  automated payment tests, to be left blank if unavailable. Never fund it with
  mainnet assets; never commit a real value. Testnet and production wallet
  configuration must be kept in clearly separate environments and never mixed.
- **No production private key in automated tests.** SPEC §26 states this
  directly.
- `.env`, `.dev.vars`, and `*.sqlite` files are gitignored. Only `.env.example`
  and (once created) `.dev.vars.example` are tracked, and they must contain
  placeholders only.

If you are configuring a deployment: generate `BACKEND_AUTH_SECRET` with
`openssl rand -hex 32`, set the recipient to your own public address, and keep
every key material outside the repository.

## 9. Status and remaining configuration

**Implemented**

- The x402 gate on `POST /v1/evidence` and on paid `POST /mcp` calls.
- Configurable network, recipient, facilitator, and price from Worker `env`.
- Memoised middleware construction.
- Test/production separation across `wrangler.jsonc` environment blocks.
- The doubly-guarded development bypass with a visible response marker.
- `payment-signature` forwarding to the backend and `payment-response`
  pass-through to the client.
- Payment error codes and their HTTP statuses.

**Not yet done**

- **No on-chain payment has been demonstrated.** No funded Base Sepolia
  settlement and no mainnet settlement has been executed against a deployment.
  Do not describe the payment flow as verified.
- **No automated x402 payment test exists.** SPEC §26 asks for two: a request
  without payment producing `402`, and a valid testnet payment succeeding.
  Neither is written.
- **Literal test addresses are still present in `wrangler.jsonc`** — see the
  defect note in §5.
- The `402` behaviour is **observed, not inferred**: `scripts/worker-smoke.sh`
  drives a live Worker and asserts the 402 plus a decoded `PAYMENT-REQUIRED`
  (0.03 USDC on the CAIP-2 id `eip155:84532`). On-chain settlement
  is still not demonstrated.

`.dev.vars.example` now exists at `apps/worker/.dev.vars.example` (SPEC §32) with
placeholders only.

**Required manual configuration before a real deployment**

| Item | Where | Notes |
|---|---|---|
| `X402_RECIPIENT` | Worker var | Your own **public** Base address. |
| `X402_NETWORK` | Worker var | `eip155:8453` for production. |
| `X402_FACILITATOR_URL` | Worker var | Confirm the current official facilitator for your network. |
| `X402_PRICE_USD` | Worker var | Verify it is not silently defaulting. |
| `BACKEND_AUTH_SECRET` | `wrangler secret put BACKEND_AUTH_SECRET` | Generate with `openssl rand -hex 32`. |
| `BACKEND_ORIGIN_URL` | Worker var | Your protected origin. |
| Public API domain / `MCP_PUBLIC_URL` | DNS | Use placeholders until you own a domain. |

Per SPEC §43: do not fake these, and do not claim the integration works until it
has been demonstrated.
